3. Material Pre-Release Defects / Risks

B53-01 — Concurrent grid writers can publish different accepted saves to the row and file

Classification: B. Material Pre-Release Defect / Risk. Severity: High. Confidence: High.

Files / functions: ogmap/grids.py:388, 507; save / _promote_committed.

Confirmed behavior: Each writer commits its row and marker, then reacquires the project lock to publish. Promotion does not check that the row still names that writer’s updated_at. A second save can complete in that gap; the first then overwrites its file and clears the newer marker.

Evidence: concurrent-publication-evidence.json: two real database connections, with B’s full save ordered between A’s commit and promotion. Both saves return success. Row updated_at belongs to B and unit is ft; loaded file updated_at belongs to A and contains 2000 m / Writer A, while B saved 3000 ft / Writer B. The scheduling hook forces an otherwise valid interleaving; it does not replace persistence operations.

Impact: The latest accepted save can lose its scientific file while its metadata remains accepted. Subsequent load has no surviving B stage to reconcile it. This is distinct from the former active-reader race, which passed its fresh reproduction.

Scenario: Two windows/sessions save edits to the same project grid almost together. The DB/file pair permanently describes different saves even though both users receive success.

Smallest safe fix: Check publication ownership/version under the same lock before promoting or rolling back, and serialize or reject superseded writers. Do not let an older publication overwrite a newer file or clear its marker. Keep before/after-commit recovery.

Regression tests: Two-connection/process barriers for update/update, create, rename and failure rollback. Assert row version/unit/source and file version/value/geometry agree after both writers return and after reopen; preserve the existing reader and crash-recovery cases.

B53-02 — Alias ownership checks still permit a silent transfer between concurrent additions

Classification: B. Material Pre-Release Defect / Risk. Severity: High. Confidence: High.

Files / functions: database.py:3125, 3144, 3156, 3163; add_top_alias / _alias_owner / _record_alias; analogous check/write boundary in rename_top_definition.

Confirmed behavior: The new existing-owner checks run before the write transaction. _record_alias still uses ON CONFLICT(alias) DO UPDATE SET definition_id. Another connection can acquire the previously free alias after the check and before the insert.

Evidence: alias-concurrency-evidence.json: A checks an unowned Shared legacy alias; B adds it and returns success with owner B; A then completes using its earlier check and returns success with owner A. Both are actual add_top_alias calls on two connections; the hook controls ordering only.

Impact: The single-user collision defect is fixed, but a concurrent user’s committed alias can still be silently reassigned to a different geological top. A later import/Map lookup follows the wrong identity relative to the first user’s accepted edit. No client incident or frequency is asserted.

Scenario: Two project-connected sessions add the same newly agreed legacy spelling to different definitions at nearly the same time.

Smallest safe fix: Make ownership validation and mutation atomic under a write lock or a conditional insert/conflict check. Reserve explicit reassignment for the deliberate merge path; recheck alias ownership after acquiring the lock.

Regression tests: Two-connection add/add and add/rename interleavings. Require one success and one clear conflict, preserving the first accepted owner, both sets of picks, source/notes and reopen state.

B53-03 — Alias edits do not invalidate persistent Map grid-point caches

Classification: B. Material Pre-Release Defect / Risk. Severity: High. Confidence: High.

Files / functions: database.py:53–55, 3125, 3151; ogmap/grids.py:840–872; ogcore/attribute_index.py:199, 221; ogmap/window.py:1310; CHANGE_DOMAINS / add_top_alias / remove_top_alias / kept_points / _grid_points.

Confirmed behavior: top_aliases is absent from the revision domains. Adding/removing an alias changes query meaning without changing the stamps that key Map well-point caches in memory and the project Cache folder.

Evidence: alias-cache-evidence.json: a supported Legacy source first resolves A at MD 100. After explicit Remove Other Name followed by assigning Legacy to B, fresh gather returns 1000 but kept_points returns 100, including after closing/reopening the project. All recorded revision counters are unchanged. Fixture exclusions were cleared so the one well participates.

Impact: Map’s cached control-point values can remain attached to the former geological definition after the current resolver changes. This can persist across reopen. The reproduction is a cache/display/control-point defect; manual Regrid gathers fresh points, so this does not demonstrate that the regridding algorithm itself computes from the stale cache.

Scenario: A user deliberately retires a legacy spelling from one top and assigns it to another, or adds a missing legacy alias for an imported grid. A Map opened again can show the old/empty cached point set until an unrelated relevant edit invalidates it.

Smallest safe fix: Include top_aliases in the top revision/invalidation mechanism and refresh those triggers for existing projects. Invalidate both persisted and in-memory dependent point answers without changing stored scientific grid values.

Regression tests: Prime a real project point cache, remove/add an alias, compare fresh and cached answers immediately and after reopen. Include empty-to-valid aliases, explicit reassignment, multiple wells and unrelated cache domains.

B53-04 — IHS and PPF reimports skip corrected top depths after canonical rename

Classification: B. Material Pre-Release Defect / Risk. Severity: High. Confidence: High.

Files / functions: ogcore/ihs297.py:914–945; ogcore/petra_ppf.py:1101–1124; database.py:3413; IHS _children / Petra PPF _children / _check_top_unique.

Confirmed behavior: Both native importers build existing-pick keys from canonical names but build incoming keys from the old raw vendor name. They try add rather than update; the canonical DB uniqueness check rejects it and the importer records a duplicate warning.

Evidence: native-alias-updates-evidence.json: actual IHS apply on a reduced supplied real-format fixture, then rename MDWY and correct its source-3 input from 860 to 885. Explicit overwrite leaves 860 and reports duplicate. Actual PPF scan/apply using the shipped test fixture generator, blank_only=False, rename DAKOTA then change input 7607.97622295704 to 7650: depth stays 7607.97622295704 with duplicate warning. Other records update.

Impact: Supported alias resolution prevents new duplicate definitions, but does not make these update paths correct. An explicitly requested vendor correction remains stale after normal global-top cleanup. This is surfaced as a warning, not silent whole-import success without diagnostics.

Scenario: A project’s vendor top is renamed canonically, then an updated IHS/PPF delivery uses its original name and includes a corrected depth.

Smallest safe fix: Canonicalize incoming identity before both existing-pick and within-file duplicate matching, using the shared noncreating resolver/top_pick_name where appropriate. Preserve existing source-specific update/blank-only/repeated-pick rules.

Regression tests: Real importer entry points: import, rename/merge top, reimport same vendor spelling with a changed depth and explicit updates. Verify exact intended pick ID/source is updated, blank-only preserves it, legitimate distinct sources remain, notes and unrelated records persist.

B53-05 — Repeated spaces in imported source names break Source Manager enumeration and rename

Classification: B. Material Pre-Release Defect / Risk. Severity: Medium. Confidence: High.

Files / functions: database.py:195, 3077–3111; bulk_import.py:560–583; geoworkbench/interpretation_dialogs.py:313–320; normalize_source / top_pick_sources / merge_top_pick_sources / TopSourcesDialog.fill.

Confirmed behavior: Bulk imports can retain repeated internal source spaces through SQL’s UPPER(TRIM()) trigger. Enumeration groups by that raw SQL spelling but displays normalize_source’s collapsed spelling. Different groups therefore produce the same Treeview item ID. Rename also compares the collapsed input against uncollapsed stored text.

Evidence: source-spacing-evidence.json: actual XLSX import of Acme Energy and Acme Energy reports no errors and stores both spellings. Enumeration returns two ACME ENERGY rows, each one pick. Opening the actual manager raises TclError: Item ACME ENERGY already exists. Renaming the displayed source changes only the single-space record, leaving the double-space one.

Impact: The manager can fail to open on an ordinary imported-name variation, and its displayed source/counts do not identify the records rename actually affects. No top/depth/notes corruption was demonstrated.

Scenario: A seller/vendor file contains inconsistent spacing in company/interpreter names, with picks under both variants.

Smallest safe fix: Use one normalization for storage, enumeration, grouping and matching. Aggregate counts by the normalized identity or use stable distinct row IDs if intentionally retaining raw spellings. Any cleanup must modify only formation_tops.source and preserve all pick identities/provenance outside that field.

Regression tests: Actual bulk/mapped imports with spaces, tabs, mixed case, blank/null and multiple definitions. Open the manager, assert unique rows and accurate counts, then rename/merge/reopen and compare all non-source fields, aliases/order, faults and grid bytes.

B53-06 — Oversized unnamed CArchive data can bypass fail-closed archive inspection

Classification: B. Material Pre-Release Defect / Risk. Severity: Medium. Confidence: High.

Files / functions: tools/release/check_protected.py:40, 162–175, 194–202; archive_contents / executable_problems.

Confirmed behavior: A type x entry above the size limit is replaced with four zero bytes. If its filename does not have a recognized archive extension, the zeros erase the ZIP/PYZ magic and executable_problems skips inspection without an oversized/unreadable finding.

Evidence: protection-limits-evidence.json: a real CArchive data.bin contains a 1,158-byte ZIP holding ogcore/formulas.py. At the default limit the protected source is detected. Lowering MAX_ARCHIVE_BYTES to 128 to exercise the exact oversize branch yields an empty problem list; the same payload named data.zip fails closed. No 512MB artifact was allocated; production threshold is 512MiB.

Impact: The documented size bound is not consistently fail-closed for magic-detected embedded archives. This is a confirmed checker boundary gap, not a demonstrated protected-source leak in the actual current builds. Normal type x, nesting and case variants now pass the negative tests.

Scenario: A future collected data resource is an archive without an archive suffix and exceeds the checker’s limit. It is accepted unchecked instead of clearly refusing release verification.

Smallest safe fix: Propagate an explicit over-limit/uninspectable result, or safely inspect enough header bytes before deciding whether an oversized entry is an archive. Check advertised uncompressed length as well as compressed length before extraction; preserve bounded depth/size behavior.

Regression tests: Boundary tests with a reduced configured limit for named and unnamed ZIP/PYZ type x data, compressed/uncompressed lengths, owner/customer paths, just-under/just-over limits and clean actual-package positive controls.
