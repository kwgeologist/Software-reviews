# ERROR HANDLING

Search systematically for:

- broad `except Exception`
- bare `except`
- swallowed exceptions
- `pass` after exceptions
- errors printed only to console
- operations continuing after a failed critical step
- misleading success messages
- UI state left inconsistent after an exception

Do not report broad exception handling merely because it exists.

Report it where it can conceal real failure or data corruption.

---

# THREADING / GUI SAFETY

Audit Tk/Tkinter and background work.

Look for:

- Tk calls from worker threads
- race conditions
- `after()` callbacks against destroyed widgets
- stale widget references
- focus manipulation likely to crash Tk
- background tasks modifying closed projects
- cancellation races

Pay attention to the historical Tk/focus crash risk, but judge only the current implementation.

# PERFORMANCE

Look for significant problems only.

Examples:

- O(N²) loops across large well populations
- repeated full-table scans
- loading entire large seismic/PPF files unnecessarily
- repeated database commits in large loops
- per-feature redraw during bulk import
- expensive calculations on the UI thread
- unbounded caches
- retained large NumPy arrays after windows close

Do not recommend micro-optimization.

# SEVERITY DEFINITIONS

## CRITICAL

Likely to cause:

- project corruption
- significant silent data loss
- unrecoverable project failure
- severe security exposure

under realistic normal use.

## HIGH

Likely functional failure in a normal supported workflow, or substantial risk of incorrect technical data.

## MEDIUM

Real defect or robustness issue but requires a less-common condition or has a reasonable workaround.

## LOW

Minor defect, edge case, confusing error handling or low-impact release issue.

## CLEANUP

Maintainability/style/dead-code issue with no demonstrated user-facing defect.

Do not promote a finding because the code is ugly.

# IMPORTANT AUDIT RULES

1. **Do not change anything.**
2. **Do not create speculative findings.**
3. Trace the actual call path before reporting a defect.
4. Search for tests before claiming something is untested.
5. Check whether apparent duplication is intentional compatibility behavior.
6. Do not treat a missing feature as a defect.
7. Do not challenge established product decisions unless the implementation contradicts them.
8. Do not suggest broad rewrites when a local fix would solve the problem.
9. Distinguish release blockers from long-term cleanup.
10. Current working behavior has priority over theoretical architectural purity.
